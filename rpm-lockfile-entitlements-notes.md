# RPM Lockfile Updates on macOS — SOLVED ✅

**TL;DR:** Register Red Hat entitlements **inside the podman machine VM**, not on macOS host.

## Quick Start (macOS)

```bash
# 1. Setup credentials on macOS host
make setup-entitlements

# 2. Register inside podman machine VM
make setup-entitlements-podman-machine

# 3. Run lockfile updates normally
bash scripts/rpm-lockfile-update.sh 0.21
```

**Complete guide:** [`docs/macos-rpm-lockfile-updates.md`](docs/macos-rpm-lockfile-updates.md)

---

## Why This Works

Podman on macOS runs containers in a **hidden Linux VM** (podman machine), not natively on macOS.

**The insight:** Register `subscription-manager` **inside that VM** using `podman machine ssh`. Containers launched by `podman run` execute in the same VM and see `/etc/pki/entitlement/` naturally.

## Implementation Summary

**Added scripts:**
- `scripts/setup-entitlements-podman-machine.sh` - Automates VM registration
- `docs/macos-rpm-lockfile-updates.md` - Complete usage guide

**Makefile targets:**
- `make setup-entitlements-podman-machine` - Register in VM
- `make check-entitlements-podman-machine` - Verify VM registration

**How it works:**
1. `make setup-entitlements` extracts team credentials to Podman secrets (macOS Keychain)
2. `setup-entitlements-podman-machine.sh` reads those secrets and registers inside the VM
3. RPM lockfile scripts run normally, containers see the VM's entitlement certs

## Previous Investigation Notes (Context)

### The activation-keys console error

<https://console.redhat.com/insights/connector/activation-keys/> throws "Something went wrong" for SSO logins. This is an account-type mismatch, not a bug.

**Solution:** Use the team bundle (`secrets/entitlements.asc`) instead. The org ID and activation key are already in there — no need to access the console.

### Per-person vs. shareable

| Thing | Scope |
|-------|-------|
| Org ID + activation key | Team-shared (in bundle) |
| `/etc/pki/entitlement/*.pem` | Per-system (generated by `subscription-manager register`) |

The bundle contains shareable credentials. The `.pem` files are generated locally when registering.

### Why copying certs from Linux doesn't work

1. **Mount mismatch:** Podman on macOS mounts paths from the VM, not the macOS host. Putting certs at `~/.config/submariner/entitlements/` on macOS doesn't help — containers run in the VM.
2. **Cert expiry:** Static copied certs expire. `rhsmcertd` auto-renews in the VM where they're registered.
3. **Missing dependencies:** Containers also need CA certs, repo files, etc.

**Solution:** Don't copy certs. Register in the VM and let containers use them natively.

## How Other Devs Do It

Based on this investigation, other macOS users likely:

1. ✅ **Register inside podman machine** (recommended - this guide)
2. Use a separate RHEL VM (heavier)
3. SSH to a remote Linux host (requires network)
4. Use a Linux laptop for this specific task

The podman machine approach is the lightest-weight macOS-native solution.
